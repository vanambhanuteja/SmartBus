# Database documentation

Schema: `database/01_schema.sql` · Seed: `database/02_seed.sql` (generated by `database/generate_seed.py` from `database/seed/*.csv`). ER diagram: `docs/diagrams/diagrams.md`.

**Verified:** both files were loaded into a real PostgreSQL 16 server in the build sandbox without errors (12 routes, 30 stops, 65 route-stop links, 24 buses, 288 trips, 288 synthetic reports). A `CHECK` constraint rejected an out-of-range occupancy (120) as expected.

## Relationships
* **Routes ↔ Bus_Stops: many-to-many** through `Route_Stops` (with `stop_sequence`; unique per route) – a stop can be on many routes.
* **Routes → Trips ← Buses:** a route can be served by **many buses**, and a bus runs many trips. `Trips` = one bus on one route at one departure time (`UNIQUE(bus_id, departure_time)`).
* **Trips → Crowd_Reports:** many reports per trip (`trip_id` optional because a passenger may report by route only).
* **Users → Crowd_Reports:** a user submits many reports (`user_id` nullable, `ON DELETE SET NULL`).
* **Routes → Predictions:** stored forecasts per route for later analytics.

## Design notes
* Constraints: role ∈ {PASSENGER, ADMIN}; occupancy 0–100; crowd_level ∈ {LOW…OVERCROWDED}; lat/lon ranges; capacity > 0.
* Indexes: `(route_id, reported_at DESC)` on reports, `trip_id`, `trips(route_id)`, `predictions(route_id, created_at DESC)`.
* `crowd_reports.source` is `PASSENGER` (real) or `SYNTHETIC` (simulated) so **real observations can replace synthetic ones** and analytics can filter them.
* Passwords are BCrypt hashes. No admin is seeded in SQL: the backend creates it from `ADMIN_EMAIL`/`ADMIN_PASSWORD`.
* PostGIS was **not** used: plain latitude/longitude doubles are enough for markers and polylines (no spatial queries needed).
* Seed network: illustrative Mysuru localities with **approximate, unverified** coordinates and invented `SB-xx` codes (see `database/seed/README.md`; `database/tools/fetch_osm_stops.py` fetches real OSM stops when run with internet access).
